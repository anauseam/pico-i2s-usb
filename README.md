# pico-i2s-usb

Raspberry Pi Pico 2 (RP2350) I2S-to-USB UAC2 Audio Interface

## Overview

This repository contains bare-metal C firmware that turns a Raspberry Pi Pico 2 and a standard **24-bit I2S** Analog-to-Digital Converter (ADC) into a driverless, plug-and-play USB audio interface.

It reads standard I2S digital audio data from an external ADC (such as the PCM1808 or TAA5242) and streams it to a host computer over USB using the USB Audio Class 2.0 (UAC2) standard. The host (Windows, macOS, or Linux) recognizes the Pico as a standard USB microphone or line-in device — no drivers required.

> [!NOTE]
> **Host OS Compatibility**
> UAC2 is natively supported (driverless) on **macOS**, **Linux**, and **Windows 10 (version 1703 and later) and 11**.
> **Older Windows versions** require a third-party UAC2 driver. If they must be supported, consider reworking the descriptors to target UAC1.
>
> **Tested on Linux only.** macOS and Windows support UAC2 natively, so the
> device should work on them too, but the maintainer has not tested it there.

For the design rationale and open observations, see
[ARCHITECTURE.md](ARCHITECTURE.md). For contribution guidelines, see
[CONTRIBUTING.md](CONTRIBUTING.md).

## Quick Start

If you simply want to build a USB audio interface and do not need to modify the code, follow these steps. We will use a common PCM1808 ADC with an external oscillator as our example.

> [!NOTE]
> **Default Configuration**
> In the default project code, we assume the following I2S configuration:
>
> - **I2S Mode:** The ADC is the I2S Controller (Master) and the Pico is the Target (Slave).
> - **MCLK:** Provided by an external oscillator connected to the ADC, not generated by the Pico.
> - **Sample Rate:** 48 kHz.
> - **I2S Format:** Standard I2S (1-bit delay), not Left/Right-Justified.
>
> To change the pins, sample rate or MCLK source, see [Configuration](#configuration).

### 1. Install the Firmware

1. Download the latest `pico-i2s-usb.uf2` file from the [Releases](../../releases) page.
2. Hold down the **BOOTSEL** button on your Raspberry Pi Pico 2 and plug it into your computer via USB.
3. The Pico will appear as a removable USB drive.
4. Drag and drop the `.uf2` file onto the drive. The Pico will automatically reboot and install the firmware.

### 2. Hardware Wiring (PCM1808 Example)

Below is the default wiring guide for the Pico 2 and the PCM1808 ADC with an external oscillator.

#### Data and Clock Connections

| Pico 2 Pin | PCM1808 Pin | Function |
| :--- | :--- | :--- |
| `GPIO 2` | `DOUT` | Digital Audio Data Input |
| `GPIO 10` | `BCK` | Bit Clock (from ADC) |
| `GPIO 11` | `LRCK` | Left/Right Word Clock (from ADC) |

> [!NOTE]
> Since the ADC is the I2S Controller in the default configuration, the external oscillator provides `SCK` (MCLK) directly to the PCM1808. The Pico does not need a connection to MCLK.

#### Power and Ground

| Pico 2 Pin | PCM1808 Pin | Function |
| :--- | :--- | :--- |
| `GND` | `GND` | Common Ground |
| `3V3(OUT)` | `3.3V` / `VDD` | Digital Logic Power |
| `VBUS` | `5V` / `VCC` | Analog Audio Power (From USB) |

#### Hardware Configuration (PCM1808 Specific)

> [!NOTE]
> If you are using a different ADC, you must consult its datasheet to find out how to configure it for Controller/Master Mode and Standard I2S Data Format.

To configure the PCM1808 as the I2S Controller and to output standard I2S data format, set the following pins:

- Connect **FMT** (sometimes printed as FMY) to `GND` (I2S format).
- Connect **MD0** to `3.3V` (Controller mode, 512 fS).
- Connect **MD1** to `GND` (Controller mode, 512 fS).

At 512 fS, a 48 kHz sample rate needs a 24.576 MHz oscillator (512 × 48 kHz).

Once wired, plug the Pico into your computer. It will appear in your system audio settings as a USB input device.

## Configuration

Every setting lives in one file, [`src/audio_config.h`](src/audio_config.h). You don't need to change any other code.

1. Open the file and change the setting's value. For example, to move the bit clock to `GPIO 6`, edit this line:

   ```c
   #define PIN_I2S_BCLK 6
   ```

2. [Build the firmware](#building-from-source).
3. Flash the new `pico-i2s-usb.uf2`.

The firmware on the Releases page uses the defaults below.

| Setting | Default | What it does |
| :--- | :--- | :--- |
| `PIN_I2S_DIN` | `2` | I2S data into the Pico (the ADC's `DOUT`) |
| `PIN_I2S_BCLK` | `10` | I2S bit clock |
| `PIN_I2S_LRCK` | `11` | I2S frame clock (also called FSYNC or WS) |
| `MCLK_SOURCE` | `MCLK_SOURCE_EXTERNAL` | Where the ADC's master clock comes from: `MCLK_SOURCE_EXTERNAL` or `MCLK_SOURCE_PICO`. See [Clock Architecture](#clock-architecture). |
| `PIN_MCLK` | `21` | MCLK output, used with `MCLK_SOURCE_PICO` |
| `AUDIO_RATES` | `AUDIO_RATE_48000` | The sample rate: `AUDIO_RATE_44100`, `AUDIO_RATE_48000` or `AUDIO_RATE_96000`. Set one, matching how your ADC is wired. |
| `AUDIO_BUFFER_FRAMES` | `128` | Frames per DMA buffer (one sample per channel each) |
| `AUDIO_DEBUG_LOGGING` | `0` | `1` prints raw samples over UART. See [Debugging](#debugging). |

Leave the other settings in the file at their defaults. They belong to features that are not implemented yet.

On a Pico 2, these pins are allowed:

| Setting | Allowed GPIOs |
| :--- | :--- |
| `PIN_I2S_DIN`, `PIN_I2S_BCLK`, `PIN_I2S_LRCK` | 2 to 22 and 26 to 28. They don't have to be adjacent. |
| `PIN_MCLK` | 13, 15 or 21 |

Two settings can't use the same GPIO. The other GPIOs are taken: `GPIO 0` and `1` carry the debug console, and the Pico 2 board itself uses `GPIO 23`, `24`, `25` and `29`.

If a setting can't work, the build stops with a message that names the setting to change.

## Technical Details

This firmware is built using the official Raspberry Pi Pico C/C++ SDK and the TinyUSB stack. It uses a custom PIO (Programmable I/O) state machine program to capture I2S audio data, a DMA ping-pong buffer to move audio into memory without per-sample CPU work (the CPU services one interrupt per buffer), and TinyUSB's UAC2 audio class driver to stream the data to the host.

### Data Pipeline

The complete audio path from analog signal to host application:

```text
Analog Signal
    │
    ▼
┌────────────┐   MCLK/BCLK/LRCK    ┌────────────┐   PIO RX FIFO   ┌──────────────┐
│  External  ├────────────────────►│  PIO State │────────────────►│  DMA Engine  │
│    ADC     │  I2S Data (DIN)     │  Machine   │ (32-bit words)  │ (Ping-Pong)  │
└────────────┘                     └────────────┘                 └──────┬───────┘
                                                                         │
                                                           DMA IRQ fires │ buffer ready
                                                                         ▼
┌──────────┐   USB ISO Packets   ┌────────────┐   tud_audio_write  ┌─────────────┐
│   Host   │◄────────────────────┤  TinyUSB   │◄───────────────────┤  Main Loop  │
│   (PC)   │   (384 bytes/1ms)   │  UAC2 EP   │   (1024 bytes)     │ (Conductor) │
└──────────┘                     └────────────┘                    └─────────────┘
```

1. **PIO Capture** — A custom PIO state machine receives I2S data on external BCLK/LRCK edges, packing each 32-bit sample into the PIO RX FIFO.
2. **DMA Ping-Pong** — Two DMA channels are chained together. While one fills a 256-word buffer from the PIO FIFO, the other's completed buffer is available for consumption. A DMA completion interrupt signals the main loop.
3. **Main Loop** — Polls for completed DMA buffers and writes them directly into TinyUSB's internal FIFO via `tud_audio_write()`. The I2S data is passed through without format conversion — the UAC2 descriptors tell the host how to interpret the 32-bit containers (24-bit audio in a 32-bit sample slot).
4. **USB Transmission** — TinyUSB autonomously drains its 4096-byte software FIFO into Isochronous IN packets at the USB Full-Speed 1ms frame rate. The FIFO decouples the 2.66ms DMA burst rate from the 1ms USB polling rate.

### USB Audio Implementation

The USB stack presents the device as a **stereo UAC2 microphone** using the following descriptor topology:

```text
Input Terminal (Generic Mic, ID=1)
    │
    ▼
Feature Unit (ID=2, Mute/Volume stubs)
    │
    ▼
Output Terminal (USB Streaming, ID=3) ──► Isochronous IN Endpoint (0x81)
    │
Clock Source (Internal Fixed, ID=4)
```

**Key parameters:**

| Parameter | Value |
| :--- | :--- |
| USB Speed | Full Speed (12 Mbps) |
| Audio Format | PCM, Type I |
| Container Size | 32-bit (4 bytes per sample) |
| Bit Depth | 24-bit (in 32-bit container) |
| Channels | 2 (Stereo: Front Left, Front Right) |
| Sample Rate | Fixed, single rate (`AUDIO_RATES` in `audio_config.h`) |
| Isochronous Mode | Asynchronous |
| Max EP Size | `(AUDIO_RATE_MAX / 1000 + 1) × AUDIO_CHANNELS × 4` bytes |
| SW FIFO | 4096 bytes |

#### TinyUSB Configuration (`tusb_config.h`)

The TinyUSB stack requires several non-default configuration choices on the RP2350. See `docs/internals/06-workarounds.md` for the full proof behind each item.

- **Flow control is disabled** (`CFG_TUD_AUDIO_EP_IN_FLOW_CONTROL 0`). TinyUSB's flow control path in `audiod_calc_tx_packet_sz()` requires `sample_rate_tx` to be initialised by receiving a `SET_CUR(SAM_FREQ)` command from the host. For a fixed-frequency device, Linux never sends this command: the Clock Source descriptor declares the frequency control as read-only (`AUDIO_CTRL_R`), and the Linux UAC2 driver (`sound/usb/clock.c`) correctly skips `SET_CUR` for read-only controls. Because `sample_rate_tx` stays `0`, TinyUSB computes a packet size of `0` permanently. This is a proven structural flaw in TinyUSB's UAC2 flow control for fixed-rate devices. See `docs/internals/06-workarounds.md §6.1` for the full proof.

#### Isochronous Endpoint Management (`usb_audio.c`)

TinyUSB's RP2040/RP2350 DCD uses `TUP_DCD_EDPT_ISO_ALLOC`, which pre-allocates Isochronous endpoints and skips the standard close/reopen sequence during `SET_INTERFACE` alternate setting transitions. This leaves the hardware DPRAM `USB_BUF_CTRL_AVAIL` bit set after the host deactivates the stream (Alt 0). When the host reactivates (Alt 1), the DCD attempts to set the bit again, triggering a hardware panic (`ep 81 was already available`). This was confirmed via UART debug output.

`tud_audio_set_itf_close_EP_cb` manually clears the `AVAIL` and `FULL` bits in the RP2350 USB DPRAM buffer control registers for the audio endpoint before TinyUSB reactivates it.

All remaining UAC2 control callbacks (GET/SET for entities, endpoints, and interfaces) return `false` to correctly STALL unsupported features, complying with the standard.

### Clock Architecture

The system clock `clk_sys` runs at **61.44 MHz**: `pll_sys` multiplies the 12 MHz crystal by 128 and divides the result by 5 × 5. The MCLK the Pico can generate divides from it by an integer. For the derivation, see [ARCHITECTURE.md §3.3](ARCHITECTURE.md).

I2S role: the ADC generates BCLK and LRCK and the Pico is the **Target**; its PIO state machine, running at the full `clk_sys`, samples the data on their edges. The Pico-as-Controller role is not implemented yet.

The ADC's master clock (MCLK) comes from one of two places, selected by `MCLK_SOURCE` in `src/audio_config.h`.

#### External Oscillator (Default)

`MCLK_SOURCE_EXTERNAL`. An oscillator feeds the ADC's MCLK input, and the ADC derives BCLK and LRCK from it. Any sample rate the ADC and the oscillator support works, including 44.1 kHz.

#### Pico-Generated MCLK

`MCLK_SOURCE_PICO`. The Pico divides `clk_sys` by 5 in a CLK_GPOUT clock generator and outputs **12.288 MHz** (256 × 48 kHz) at a 50 % duty cycle on `PIN_MCLK` (default `GPIO 21`). The ADC derives BCLK and LRCK from this clock. Supported sample rates:

- **48 kHz** with an ADC that runs at 256 fS. On the PCM1808, connect **MD0** and **MD1** to `3.3V` (Controller mode, 256 fS).
- **96 kHz** with an ADC whose own PLL makes it from 12.288 MHz. The PCM1808 cannot: at 96 kHz it needs a 24.576 MHz clock.

`PIN_MCLK` must be a CLK_GPOUT pin. On the Pico 2 these are `GPIO 13`, `15` and `21`.

### Debugging

Set `AUDIO_DEBUG_LOGGING` to `1` in `src/audio_config.h` to enable periodic
UART logging in the main loop. When enabled, one line is printed
approximately every 1.3 seconds:

```text
[Audio Data] L: 0x1A182100 | R: 0x0000F300 | overflow=38449 | overrun=0
```

- `L` and `R`: the first left and right samples of the latest DMA buffer.
  They should change from line to line.
- `overflow`: DMA buffers dropped because TinyUSB's FIFO was full. It also
  climbs while the host isn't recording, so compare it at the start and end
  of a recording; it shouldn't change during one.
- `overrun`: DMA buffers overwritten before the main loop took them. It
  should read 0.

Logging doesn't hold up the audio path.

UART output goes to UART0: TX on `GPIO 0`, RX on `GPIO 1`, 115200 baud. Read it with a Raspberry Pi Debug Probe or a USB-to-serial adapter; the Pico's own USB port carries only audio.

> [!WARNING]
> `CFG_TUSB_DEBUG` in `tusb_config.h` must stay at `0`. TinyUSB logs through
> `printf`, which waits for the UART, so its per-transfer log lines hold up
> USB long enough to drop audio; at debug level 2 the stream arrived at a
> fraction of its rate. This is a latency limit, not a TinyUSB bug.

### Building from Source

This project uses standard CMake and relies on the official Raspberry Pi Pico SDK.

**Prerequisites:**

- Raspberry Pi Pico SDK (v2.2.0+)
- Appropriate toolchain package (`arm-none-eabi-gcc` or `riscv64-elf-gcc`)

**Standard Build Flow:**

```bash
mkdir build && cd build

# Configure (Default ARM)
cmake -DPICO_PLATFORM=rp2350 ..

# OR Configure (RISC-V)
# cmake -DPICO_PLATFORM=rp2350-riscv ..

# Build
make -j$(nproc)
```

The compiled `pico-i2s-usb.uf2` will be placed in the `build/` directory.

**Advanced Configuration:**
If your SDK or toolchain are in non-standard locations, or your toolchain uses a different naming convention (e.g., on Arch Linux), you may need to specify them manually:

```bash
cmake -DPICO_SDK_PATH=/path/to/sdk \
      -DPICO_TOOLCHAIN_PATH=/path/to/bin \
      -DPICO_GCC_TRIPLE=your-compiler-triple \
      ..
```

*Note: Pre-compiled binaries for the default configuration are available on the Releases page.*
